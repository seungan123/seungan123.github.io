## OWASP Top 10을 살펴본 이유

OWASP는 소프트웨어 보안을 개선하기 위해 자료와 도구를 공개하는 비영리 보안 커뮤니티이다. OWASP Top 10은 웹 애플리케이션의 주요 보안 위험을 10개 범주로 묶은 문서로, 개발자와 보안 담당자가 어떤 위험부터 살펴볼지 정할 때 참고한다.

2017년, 2021년, 2025년 자료를 차례로 보다 보니 외부 구성 요소와 관련된 항목이 계속 바뀌어 온 것이 눈에 들어왔다. 그래서 2025년 A03인 소프트웨어 공급망 실패를 골라 공부해 봤다. 예전에는 어떤 문제를 다뤘고 지금은 어디까지 포함하는지, 실제 사건에서는 어디서 문제가 시작됐는지도 살펴봤다.

| 연도 | 항목 | 주요 범위 |
| --- | --- | --- |
| 2017 | A09 — 알려진 취약점이 있는 구성 요소 사용 | 알려진 취약점이 있는 라이브러리와 구성 요소 |
| 2021 | A06 — 취약하고 오래된 구성 요소 | 취약점뿐 아니라 지원 종료나 관리 중단 문제 |
| 2025 | A03 — 소프트웨어 공급망 실패 | 의존성, 개발 도구, 빌드와 배포 과정 전반 |
{: .reading-table .table-cols-3 .comparison-table }

순위가 올랐다고 해서 그만큼 공격이 늘었다고 보기는 어렵다. 항목의 범위와 수집된 데이터가 함께 달라졌기 때문이다. 그래도 보안에서 챙겨야 할 대상이 넓어졌다는 점은 분명했다.

예전에는 라이브러리의 취약점을 확인하고 업데이트하는 일을 먼저 떠올렸다. 이제는 그 라이브러리를 누가 관리하고, 어떤 과정을 거쳐 내 프로그램에 들어오는지까지 봐야 한다. AI가 코드를 작성하고 패키지까지 골라 주는 환경에서는 이 문제가 어떻게 달라질지도 궁금했다.

## 소프트웨어 공급망 실패란?

A03은 소프트웨어를 만들어 배포하고 업데이트하는 과정에서 생기는 실패와 침해를 다룬다. 외부 코드에 있던 취약점뿐 아니라 누군가 일부러 넣은 악의적인 변경도 여기에 들어간다.

### 내가 작성한 코드 밖에도 의존하는 것이 있다

프로그램 하나가 사용자에게 전달되기까지는 여러 단계를 거친다.

외부 패키지 선택 → 코드 저장소 → 빌드와 테스트 → 결과물 저장 → 배포와 업데이트

이 과정에는 라이브러리, IDE 확장 프로그램, 빌드 도구, CI/CD, 배포 서버 등이 관여한다. 내가 작성한 코드에 문제가 없어도 중간 단계에서 코드나 결과물이 바뀌면, 사용자는 결국 다른 프로그램을 받게 된다.

라이브러리를 설치하면 그 라이브러리가 사용하는 전이 의존성도 함께 들어올 수 있다. 같은 프로세스에 로드된 라이브러리는 애플리케이션의 권한으로 동작하고, 설치 스크립트가 허용된 환경에서는 설치하는 순간 코드가 실행되기도 한다. 직접 읽어 보지 않은 코드가 개발 환경이나 서비스의 일부가 되는 것이다.

### 업데이트만으로 해결되지 않는 경우

알려진 취약점이 있는 구성 요소라면 보안 패치와 업데이트가 중요한 대응이다. 그런데 공격자가 관리자 계정이나 배포 경로를 장악해 악성 버전을 올리면, 업데이트가 오히려 침입 경로가 될 수 있다.

그래서 최신 버전인지와 함께 누가 배포했는지, 무엇이 바뀌었는지, 빌드와 배포 과정을 믿을 수 있는지도 봐야 한다. 그렇다고 업데이트를 계속 미루는 것도 답은 아니다. 취약한 버전을 쓰는 기간은 줄이면서 바뀐 내용을 검증하는 과정이 필요하다.

## A03의 통계는 어떻게 읽어야 할까?

### 점수표와 실제 위험은 같은 의미가 아니다

OWASP A03 페이지에는 아래와 같은 점수표가 실려 있다.

| 지표 | 값 |
| --- | --- |
| 매핑된 CWE 수 | 6개 |
| 평균 발생률 | 5.72% |
| 평균 테스트 커버리지 | 27.47% |
| 총 발생 건수 | 215,248건 |
| 매핑된 CVE 수 | 11개 |
{: .reading-table .table-cols-2 }

그런데 같은 페이지 본문에는 평균 발생률이 5.19%로 적혀 있어서 표의 값과 다르다. 여기서는 표의 수치를 그대로 옮겼고, 이 값으로 다른 항목과 순위를 따지지는 않았다.

평균 발생률은 검사한 애플리케이션 가운데 관련 약점이 발견된 비율을 바탕으로 계산한 값이다. 테스트 커버리지는 그 약점들을 얼마나 검사했는지를 나타내는 값으로, 퍼징에서 실행 경로를 재는 코드 커버리지와는 의미가 다르다.

총 발생 건수 215,248건도 OWASP가 모은 데이터 안에서 센 값이지, 전 세계에서 실제로 일어난 공급망 침해 사건의 수가 아니다. CVE 11개 역시 이 분석에 매핑된 수일 뿐, 공급망 관련 취약점이 11개라는 뜻은 아니다. 숫자가 크고 작은지만 보기보다 무엇을 기준으로 센 값인지도 함께 봐야 한다.

### 수집된 데이터에 잘 드러나지 않는 위험

공급망 침해는 애플리케이션의 기능만 검사해서는 찾기 어려울 수 있다. 저장소의 코드는 멀쩡한데 빌드 결과물만 변조됐을 수도 있고, 탈취된 정상 계정으로 악성 패키지가 배포될 수도 있다.

OWASP는 테스트 데이터의 한계를 커뮤니티 설문으로 보완하는데, A03은 이 설문에서 응답자의 50%가 1순위로 꼽은 항목이다. 수집된 건수가 적다고 덜 중요한 것은 아니라는 뜻이다.

CVE가 없다고 악성 코드도 없다고 판단하면 안 된다. 그렇다고 일부러 심은 백도어에 CVE가 붙지 않는 것도 아니어서, XZ Utils 백도어에는 `CVE-2024-3094`가 부여됐다.

## 어떤 방식으로 문제가 발생할까?

### 외부 패키지와 의존성

취약한 라이브러리를 쓰거나 악성 패키지를 설치하는 데서 문제가 시작될 수 있다. 유명 패키지와 이름이 비슷한 가짜 패키지를 올려 두고 설치 실수를 노리는 방식도 여기에 들어간다.

그래서 직접 고른 패키지만 확인해서는 부족하다. 그 패키지가 다시 가져오는 의존성까지 봐야 내 프로그램에 실제로 어떤 코드가 들어오는지 알 수 있다.

### 관리자 계정과 프로젝트 운영

공격자가 패키지 관리자의 계정을 탈취하면 정상 프로젝트의 배포 권한을 그대로 쓸 수 있다. 프로젝트에 기여하며 신뢰를 얻은 사람이 악성 변경을 넣는 경우도 있다.

이럴 때는 익숙한 패키지 이름이나 관리자 이름만 보고 안전하다고 믿기 어렵다. 누가 변경을 승인했는지, 배포 권한은 어떻게 관리되는지도 함께 봐야 한다.

### 빌드와 배포 과정

소스 코드가 검토를 통과했어도 빌드 환경이 침해되면 결과물에 다른 코드가 섞일 수 있다. 배포 서버나 업데이트 파일이 변조되면 사용자는 공식 경로로 악성 결과물을 받게 된다.

특히 CI/CD에 저장소 접근 권한, 배포 권한, 클라우드 인증 정보가 한곳에 모여 있으면 침해 범위가 커질 수 있다. 작업마다 권한을 나누고, 빌드 환경이 필요 없는 비밀 정보에는 접근하지 못하게 막아 두는 것이 좋다.

## 실제 사례로 살펴보기

### SolarWinds — 빌드 과정에 삽입된 악성 코드

2020년에 드러난 SolarWinds 사건에서는 Orion 소프트웨어의 빌드 과정에 악성 코드가 들어갔고, 이 코드가 정상 업데이트를 통해 고객에게 전달됐다. 공격자가 공급자의 개발과 배포 과정을 이용해 여러 고객 조직에 접근한 사례이다.

공급자의 빌드 환경 침해 → 악성 코드가 포함된 업데이트 배포 → 고객 시스템 침해 순으로 이어졌다.

업데이트를 만드는 환경이 침해되면 이를 믿고 설치한 고객까지 영향을 받게 된다. 빌드 서버의 접근 권한을 제한하고, 코드 변경과 배포 승인을 나누는 이유도 여기에 있다. 업데이트를 받는 쪽에서도 일부 환경에 먼저 적용해 이상 징후를 살피면, 침해가 한꺼번에 퍼질 위험을 줄일 수 있다.

### Log4Shell — 널리 쓰이는 구성 요소의 취약점

2021년에 공개된 `CVE-2021-44228`은 Java 로깅 라이브러리 Log4j 2의 취약점이다. 영향을 받는 버전과 환경에서는 공격자가 제어하는 문자열이 로그로 처리될 때 JNDI 조회를 거쳐 원격 코드 실행까지 이어질 수 있었다.

이 경우는 평소에 잘 쓰던 구성 요소 자체에 취약점이 있었다. Log4j를 직접 추가하지 않았어도 다른 구성 요소를 통해 들어와 있을 수 있다. 그래서 내 프로그램에 Log4j가 포함돼 있는지, 어떤 의존성을 통해 들어왔는지부터 확인해야 한다.

이때 SBOM과 의존성 분석으로 사용 여부와 버전을 찾을 수 있다. 목록을 만들었다고 취약점이 사라지는 것은 아니므로, 영향을 받는 서비스에 보안 패치를 적용하는 데까지 이어져야 한다.

### XZ Utils — 신뢰받던 배포물에 숨겨진 백도어

2024년에는 XZ Utils 5.6.0과 5.6.1의 배포용 압축 파일에서 악성 코드가 발견됐다. 빌드 과정에서 작동하는 장치를 넣어, 특정 환경에서 만들어지는 `liblzma`에 악성 코드가 포함되도록 한 사건이다. 모든 리눅스 시스템이 영향을 받은 것은 아니고, 당시 문제 버전은 주로 일부 배포판의 개발용이나 시험용 버전에 들어가 있었다.

저장소에서 검토한 코드와 실제 배포용 파일의 내용이 다를 수 있다는 점이 인상적이었다. 이런 차이는 패키지 이름과 버전만 봐서는 알기 어렵다. 배포용 파일에 무엇이 추가됐는지, 빌드 스크립트는 어떻게 바뀌었는지도 살펴봐야 한다. 내가 설치할 파일이 어떤 소스와 환경에서 만들어졌는지까지 확인하는 이유를 알 수 있었다.

### Bybit — 외부 지갑 서비스의 침해

2025년 2월 Bybit에서 약 15억 달러 규모의 가상자산이 탈취됐다. FBI는 이 사건의 배후로 북한을 지목했다.

Bybit가 당시 공개한 조사 내용에 따르면, Safe 개발자의 인증 정보가 침해됐고 공격자는 Safe{Wallet} 인프라에 접근해 서명자가 악성 거래를 승인하도록 속였다.

이 사건을 보면서 여러 사람이 확인하고 승인하는 것만으로 충분하지 않을 수도 있겠다는 생각이 들었다. 승인 화면 자체가 변조되면 모두가 같은 잘못된 내용을 보고 승인할 수 있기 때문이다. 서비스 제공자의 계정과 배포 환경을 보호하는 일에 더해, 서명할 거래의 대상과 내용을 독립된 경로로 한 번 더 확인하는 것도 중요하다.

네 사건은 침입 방식이 서로 다르다. 그래도 직접 개발한 코드만 봐서는 외부 구성 요소나 공급자의 환경에서 시작되는 위험을 놓칠 수 있다는 점은 같았다.

## 어떻게 대응해야 할까?

### 사용하는 구성 요소부터 파악하기

문제가 된 라이브러리가 내 서비스에 들어 있는지조차 모르면 영향을 판단하기 어렵다. SBOM으로 구성 요소와 버전, 의존 관계를 기록해 두고, 바뀔 때마다 갱신한다. 목록이 있으면 취약점 정보와 보안 공지를 연결해 확인할 수 있다. OWASP도 전이 의존성까지 포함한 구성 요소 관리와 지속적인 모니터링을 권고한다.

쓰지 않는 의존성을 정리하면 확인할 범위도 줄어든다. 관리가 중단된 라이브러리는 계속 써도 되는지 검토하고, 필요하면 대체할 계획을 세운다.

### 업데이트를 검증하는 과정 만들기

버전과 잠금 파일을 관리해 의도하지 않은 변경을 줄이고, 업데이트할 때는 바뀐 내용과 보안 공지를 확인한다. 테스트 환경에서 호환성을 확인한 뒤 운영 환경에 적용하는 과정도 필요하다.

버전을 고정한다고 안전해지는 것도 아니다. 이미 알려진 취약점이 있는 버전을 계속 쓰면 위험은 그대로 남는다. 공식 배포 경로와 서명 확인도 도움이 되지만, 정당한 배포 권한 자체가 침해된 경우까지 막아 주지는 못한다.

### 계정과 CI/CD의 권한 줄이기

개발자 계정과 코드 저장소에 MFA를 적용하고, 비밀번호나 키가 코드에 남지 않도록 관리한다. 빌드와 테스트를 하는 작업과 운영 환경에 배포하는 작업의 권한을 나누고, 중요한 변경과 배포에는 검토 절차를 둔다.

배포 결과물의 출처와 생성 과정을 기록해 두면, 문제가 생겼을 때 어떤 코드와 환경에서 만들어졌는지 추적하기 쉽다. 개발 도구, 플러그인, CI/CD 설정 변경도 이 기록에 포함해 두는 것이 좋다.

### 운영 중에도 확인하기

공급망은 한 번 점검하고 끝낼 수 있는 대상이 아니다. 새 버전이 나오고, 관리자가 바뀌고, 몰랐던 취약점이 새로 공개된다. 보안 공지를 계속 확인하고, 영향을 판단해 업데이트하거나 되돌릴 수 있는 절차를 유지해야 한다.

## AI는 공급망 보안을 더 위험하게 만들까?

### 패키지를 추천하는 AI도 검토 대상이다

코드 생성 모델이 존재하지 않는 패키지 이름을 제안하는 패키지 환각을 분석한 연구가 있다. 공격자가 반복해서 제안되는 이름을 먼저 등록해 두면, 사용자가 AI의 답변을 따라 악성 패키지를 설치할 수 있다.

패키지 이름이 실제로 있다고 해서 확인이 끝나는 것도 아니다. 내가 의도한 프로젝트인지, 공식 배포처가 맞는지, 유지보수가 되고 있는지 살펴봐야 한다. AI가 설치와 실행까지 맡는다면 이 확인을 어느 단계에서 할지도 정해 둬야 한다.

### 방어를 도울 가능성과 남는 과제

AI는 코드 변경을 요약하거나, 취약점 공지와 프로젝트의 의존성 목록을 비교하거나, 수정안을 검토하는 일을 도울 수 있다. 하지만 제안이 정확한지와 실제 환경에서 문제가 해결됐는지는 따로 확인해야 한다.

내 생각에는 AI를 쓰느냐보다 AI에 어떤 권한을 주고 어떤 검토를 거치게 하느냐가 더 중요하다. 패키지 선택부터 운영 환경 배포까지 자동화하면서 확인 절차를 빼 버리면 실수도 그만큼 빠르게 퍼질 수 있다. 반대로 반복적인 확인에 AI를 쓰고 중요한 변경을 검증한다면 방어에 도움이 될 수 있다.

취약점을 찾은 뒤에도 수정안을 검토하고, 호환성을 확인하고, 배포하는 일이 남아 있다. AI가 문제를 빠르게 찾아내더라도 오픈소스 관리자가 이를 검토할 시간이 부족하면 실제 수정과 배포는 늦어질 수 있다. 발견 속도뿐 아니라 그 뒤의 작업을 어떻게 이어 갈지도 중요해 보였다.

## 배운 점과 느낀 점

공부하기 전에는 보안이 내가 작성한 코드를 안전하게 만드는 일이라고 생각했는데, 무엇을 믿고 쓰는지 결정하는 것도 보안의 일부였다. 패키지를 설치하는 명령어 한 줄 뒤에는 그 패키지의 관리자와 의존성, 빌드와 배포 과정이 연결돼 있었다.

나도 CTF나 과제를 할 때 검색해서 나온 패키지를 확인 없이 설치하곤 했다. 앞으로는 AI가 추천하는 패키지라도 설치하기 전에 공식 프로젝트인지, 어떤 의존성이 함께 들어오는지 한 번 더 확인해 봐야겠다.

이번에는 개념과 사례 위주로 공부했으니 다음에는 내 프로젝트의 의존성을 직접 확인해 보고 SBOM으로 어떤 정보를 볼 수 있는지도 살펴볼 생각이다. 이번 OWASP Top 10에 새로 추가된 A10 부적절한 예외 처리도 이어서 공부해 보겠다.
