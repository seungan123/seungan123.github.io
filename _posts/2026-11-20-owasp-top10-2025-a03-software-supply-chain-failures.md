## OWASP Top 10을 살펴본 이유

OWASP는 소프트웨어 보안을 개선하기 위해 자료와 도구를 공개하는 비영리 보안 커뮤니티이다. OWASP Top 10은 웹 애플리케이션의 주요 보안 위험을 10개 범주로 정리한 문서로, 개발자와 보안 담당자가 어떤 위험을 우선 살펴봐야 하는지 이해하는 데 도움을 준다.

2017년, 2021년, 2025년 자료를 차례로 살펴보면서 외부 구성 요소와 관련된 항목의 변화가 눈에 들어왔다. 이 글에서는 2025년의 A03 소프트웨어 공급망 실패를 중심으로, 다루는 범위가 어떻게 넓어졌는지와 실제 사례에서 무엇을 점검해야 하는지 정리했다.

| 연도 | 항목 | 주요 범위 |
| --- | --- | --- |
| 2017 | A09 — 알려진 취약점이 있는 구성 요소 사용 | 알려진 취약점이 있는 라이브러리와 구성 요소 |
| 2021 | A06 — 취약하고 오래된 구성 요소 | 취약점뿐 아니라 지원 종료·관리 중단 문제 |
| 2025 | A03 — 소프트웨어 공급망 실패 | 의존성, 개발 도구, 빌드와 배포 과정 전반 |
{: .reading-table .table-cols-3 .comparison-table }

순위가 올랐다는 사실만으로 공격이 그만큼 늘었다고 볼 수는 없다. 항목의 범위와 수집된 데이터도 달라졌기 때문이다. 다만 무엇을 보안의 대상으로 봐야 하는지가 넓어졌다는 점은 분명했다.

예전에는 사용하는 라이브러리의 취약점을 확인하고 업데이트하는 일을 먼저 떠올렸다. 이제는 그 라이브러리를 누가 관리하고, 어떤 과정을 거쳐 내 프로그램에 들어오는지도 살펴봐야 한다. AI가 코드를 작성하고 패키지까지 골라 주는 환경에서는 이 문제가 어떻게 달라질지도 궁금해졌다.

## 소프트웨어 공급망 실패란?

OWASP의 A03은 소프트웨어를 만들고 배포·업데이트하는 과정에서 생기는 실패와 침해를 다룬다. 외부 코드의 취약점뿐 아니라 악의적인 변경도 포함한다.

### 내가 작성한 코드 밖에도 의존하는 것이 있다

프로그램 하나가 사용자에게 전달되기까지는 여러 단계를 거친다.

외부 패키지 선택 → 코드 저장소 → 빌드·테스트 → 결과물 저장 → 배포·업데이트

이 과정에는 라이브러리, IDE 확장 프로그램, 빌드 도구, CI/CD, 배포 서버 등이 관여한다. 내가 작성한 코드에 문제가 없어도, 중간 단계에서 코드나 결과물이 바뀌면 사용자는 다른 프로그램을 받게 된다.

라이브러리를 설치할 때는 그 라이브러리가 사용하는 전이 의존성도 함께 들어올 수 있다. 같은 프로세스에 로드된 라이브러리는 애플리케이션의 권한으로 동작하며, 설치 스크립트가 허용된 환경에서는 설치 과정에서 코드가 실행되기도 한다. 직접 읽어 보지 않은 코드가 개발 환경이나 서비스의 일부가 되는 것이다.

### 업데이트만으로 해결되지 않는 경우

알려진 취약점이 있는 구성 요소를 사용하는 문제에는 보안 패치와 업데이트가 중요한 대응이다. 그러나 공격자가 관리자 계정이나 배포 경로를 장악해 악성 버전을 올리면, 업데이트 자체가 침입 경로가 될 수 있다.

따라서 최신 버전인지 확인하는 것과 함께, 배포 주체와 변경 내용, 빌드·배포 과정의 신뢰성도 살펴봐야 한다. 그렇다고 업데이트를 계속 미루는 것이 답은 아니다. 취약한 버전의 사용 기간을 줄이면서 변경 사항을 검증하는 과정이 필요하다.

## A03의 통계는 어떻게 읽어야 할까?

### 점수표와 실제 위험은 같은 의미가 아니다

OWASP A03 영문 페이지의 점수표에서 주요 항목을 옮기면 다음과 같다. 아래 값은 2026년 11월 25일 확인한 표를 기준으로 했다.

| 지표 | 값 |
| --- | --- |
| 매핑된 CWE 수 | 6개 |
| 평균 발생률 | 5.72% |
| 평균 테스트 커버리지 | 27.47% |
| 총 발생 건수 | 215,248건 |
| 매핑된 CVE 수 | 11개 |
{: .reading-table .table-cols-2 }

다만 같은 페이지의 배경 설명에는 평균 발생률이 5.19%로 적혀 있어 표와 일치하지 않는다. 그래서 이 글에서는 표의 수치를 기준으로 표시하고, 이 값만으로 다른 항목과의 정확한 순위를 비교하지 않았다.

평균 발생률은 검사한 애플리케이션에서 관련 약점이 발견된 비율을 바탕으로 계산한 값이다. 테스트 커버리지는 해당 약점들이 얼마나 검사됐는지를 나타내며, 퍼징에서 실행 경로를 측정하는 코드 커버리지와는 의미가 다르다.

총 발생 건수 215,248건은 OWASP가 수집한 데이터에서 집계한 값이며, 전 세계에서 실제로 일어난 공급망 침해 사건의 수를 뜻하지 않는다. CVE 11개도 이 분석에 매핑된 수치이지, 공급망 관련 취약점이 11개뿐이라는 뜻이 아니다. 수치가 어떤 대상을 기준으로 집계됐는지 확인해야 위험을 과장하거나 축소해서 해석하지 않을 수 있다.

### 수집된 데이터에 잘 드러나지 않는 위험

공급망 침해는 애플리케이션의 기능만 검사해서 찾기 어려울 수 있다. 저장소에는 정상 코드가 있어도 빌드 결과물이 변조됐을 수 있고, 정상적인 계정이 탈취되어 악성 패키지를 배포할 수도 있기 때문이다.

OWASP는 테스트 데이터의 한계를 보완하기 위해 커뮤니티 설문도 활용한다. A03은 해당 설문에서 응답자의 50%가 1순위로 선택한 항목이다. 수집된 건수만으로 중요성을 판단하기 어렵다는 점을 보여 준다.

CVE가 없다는 이유로 악성 코드가 없다고 판단해서도 안 된다. 반대로 의도적으로 심어진 백도어에는 CVE가 붙지 않는다고 단정할 수도 없다. XZ Utils 백도어에도 `CVE-2024-3094`가 부여됐다.

## 어떤 방식으로 문제가 발생할까?

### 외부 패키지와 의존성

취약한 라이브러리를 사용하거나 악성 패키지를 설치하면서 문제가 시작될 수 있다. 유명 패키지와 이름이 비슷한 가짜 패키지를 등록해 설치 실수를 유도하는 방식도 여기에 해당한다.

이때 직접 선택한 패키지만 확인하면 부족하다. 그 패키지가 다시 가져오는 의존성까지 살펴봐야 내 프로그램에 어떤 코드가 들어오는지 알 수 있다.

### 관리자 계정과 프로젝트 운영

공격자가 패키지 관리자의 계정을 탈취하면 정상 프로젝트의 배포 권한을 이용할 수 있다. 프로젝트에 기여하며 신뢰를 얻은 사람이 악성 변경을 넣는 경우도 있다.

이런 상황에서는 익숙한 패키지 이름이나 관리자의 이름만으로 안전성을 판단하기 어렵다. 누가 변경을 승인했는지, 배포 권한이 어떻게 관리되는지도 중요해진다.

### 빌드와 배포 과정

소스 코드가 검토를 통과했더라도 빌드 환경이 침해되면 결과물에 다른 코드가 포함될 수 있다. 배포 서버나 업데이트 파일이 변조되는 경우에도 사용자는 공식 경로에서 악성 결과물을 받게 된다.

특히 CI/CD에 저장소 접근 권한, 배포 권한, 클라우드 인증 정보가 함께 모여 있으면 침해 범위가 커질 수 있다. 필요한 작업마다 권한을 나누고, 빌드 환경이 불필요한 비밀 정보에 접근하지 못하도록 해야 한다.

## 실제 사례로 살펴보기

### SolarWinds — 빌드 과정에 삽입된 악성 코드

2020년에 드러난 SolarWinds 사건에서는 Orion 소프트웨어의 빌드 과정에 악성 코드가 삽입됐고, 정상 업데이트를 통해 고객에게 전달됐다. 공격자가 공급자의 개발·배포 과정을 이용해 여러 고객 조직에 접근한 사례이다.

공급자의 빌드 환경 침해 → 악성 코드가 포함된 업데이트 배포 → 고객 시스템 침해로 이어진 것이다. 이 흐름을 보면 소스 코드 검토와 함께 빌드 서버의 접근 권한을 제한하고, 코드 변경과 배포 승인을 나누는 절차가 필요한 이유를 알 수 있다. 업데이트를 받는 조직에서도 일부 환경에 먼저 적용하고 이상 징후를 확인하면 침해가 한꺼번에 확산될 위험을 줄이는 데 도움이 된다.

### Log4Shell — 널리 쓰이는 구성 요소의 취약점

2021년 공개된 `CVE-2021-44228`은 Java 로깅 라이브러리 Log4j 2의 취약점이다. 영향을 받는 버전과 환경에서는 공격자가 제어하는 문자열이 로그 처리에 들어갔을 때 JNDI 조회를 통해 원격 코드 실행으로 이어질 수 있었다.

이 사건은 정상적으로 사용하던 구성 요소의 취약점이 문제가 된 경우이다. 직접 Log4j를 추가하지 않았더라도 다른 구성 요소를 통해 포함됐을 수 있으므로, 전이 의존성을 파악하는 일이 대응의 출발점이 된다. SBOM과 의존성 분석으로 사용 여부와 버전을 확인하고, 영향을 받는 서비스에 보안 패치를 적용하는 과정으로 연결해야 한다. 목록을 만드는 것만으로 취약점이 해결되지는 않는다.

### XZ Utils — 신뢰받던 배포물에 숨겨진 백도어

2024년에는 XZ Utils 5.6.0과 5.6.1의 배포용 압축 파일에서 악성 코드가 발견됐다. 빌드 과정에서 작동하는 장치를 통해 특정 환경의 `liblzma`에 악성 코드가 포함되도록 한 사건이다. 모든 리눅스 시스템이 영향을 받은 것은 아니며, 당시 문제 버전은 주로 일부 배포판의 개발·시험용 버전에 들어가 있었다.

저장소에서 검토한 내용과 실제 배포용 파일의 내용이 다를 수 있다는 점이 인상적이었다. 이 사례에서 점검해야 할 대상은 패키지의 이름과 버전뿐 아니라 배포용 파일에 추가된 내용과 빌드 스크립트의 변경이다. 배포물을 만드는 과정을 검토하고, 어떤 소스와 환경에서 결과물이 생성됐는지 추적할 수 있어야 한다.

### Bybit — 외부 지갑 서비스의 침해

2025년 2월 Bybit에서는 약 15억 달러 규모의 가상자산이 탈취됐다. FBI는 이 사건의 배후를 북한으로 지목했다.

Bybit가 공개한 조사 내용에 따르면 Safe 개발자의 인증 정보가 침해됐고, 공격자는 Safe{Wallet} 인프라에 접근해 서명자가 악성 거래를 승인하도록 속였다. 이 부분은 당시 공개된 조사 결과를 기준으로 정리했다.

이 사례에서 얻을 수 있는 교훈은 승인 절차가 의존하는 외부 서비스도 보호 대상이라는 점이다. 승인 화면 자체가 변조되면 여러 사람이 같은 화면을 확인하더라도 잘못된 내용을 승인할 수 있다. 서비스 제공자의 계정과 배포 환경을 보호하고, 서명할 거래의 대상과 내용을 독립된 경로로 검증하는 절차가 함께 필요하다.

네 사건은 침입 방식이 같지는 않다. 다만 직접 개발한 코드만 살펴봐서는 외부 구성 요소나 공급자의 환경에서 시작되는 위험을 놓칠 수 있다는 공통점이 있다.

## 어떻게 대응해야 할까?

### 사용하는 구성 요소부터 파악하기

문제가 된 라이브러리가 내 서비스에 들어 있는지 모르면 영향을 판단하기 어렵다. SBOM으로 구성 요소와 버전, 의존 관계를 기록하고 변경될 때 갱신해야 한다. 목록을 만든 뒤에는 취약점 정보와 보안 공지를 연결해 확인한다. OWASP도 전이 의존성을 포함한 구성 요소 관리와 지속적인 모니터링을 권고한다.

사용하지 않는 의존성을 정리하면 확인해야 할 범위도 줄어든다. 관리가 중단된 라이브러리는 계속 사용할 수 있는지 검토하고, 필요한 경우 대체할 계획을 세워야 한다.

### 업데이트를 검증하는 과정 만들기

버전과 잠금 파일을 관리해 의도하지 않은 변경을 줄이고, 업데이트할 때는 변경 내용과 보안 공지를 확인한다. 테스트 환경에서 호환성을 검사한 뒤 운영 환경에 적용하는 과정도 필요하다.

버전을 고정했다고 안전해지는 것은 아니다. 이미 알려진 취약점이 있는 버전을 계속 사용하면 위험이 남는다. 공식 배포 경로와 서명 확인도 도움이 되지만, 정당한 배포 권한 자체가 침해된 상황까지 보장하지는 못한다.

### 계정과 CI/CD의 권한 줄이기

개발자 계정과 코드 저장소에 MFA를 적용하고, 비밀번호나 키가 코드에 남지 않도록 관리한다. 빌드·테스트 작업과 운영 환경 배포 작업의 권한을 구분하며, 중요한 변경과 배포에는 검토 절차를 둔다.

배포 결과물의 출처와 생성 과정을 기록하면 문제가 생겼을 때 어떤 코드와 환경에서 만들어졌는지 추적하는 데 도움이 된다. 개발 도구, 플러그인, CI/CD 설정 변경도 이 기록에 포함할 필요가 있다.

### 운영 중에도 확인하기

공급망은 한 번 점검하고 끝나는 대상이 아니다. 새로운 버전이 나오고, 관리자가 바뀌며, 이전에는 몰랐던 취약점이 공개된다. 보안 공지를 확인하고 영향을 판단한 뒤 업데이트하거나 되돌릴 수 있는 절차를 유지해야 한다.

## AI는 공급망 보안을 더 위험하게 만들까?

### 패키지를 추천하는 AI도 검토 대상이다

AI가 존재하지 않는 패키지 이름을 제안할 수 있다는 연구가 있다. 공격자가 반복해서 제안되는 이름을 먼저 등록하면, 사용자가 AI의 답변을 따라 악성 패키지를 설치할 가능성이 생긴다. 이는 코드 생성 모델의 패키지 환각을 분석한 연구에서 다룬 위험이다.

패키지 이름이 실제로 존재한다고 해서 확인이 끝나는 것도 아니다. 내가 의도한 프로젝트인지, 공식 배포처가 맞는지, 유지보수가 이루어지는지 살펴봐야 한다. AI가 설치와 실행까지 맡는다면 이 확인을 어느 단계에서 수행할지도 정해야 한다.

### 방어를 도울 가능성과 남는 과제

AI는 코드 변경을 요약하거나, 취약점 공지와 프로젝트의 의존성 목록을 비교하고, 수정안을 검토하는 일을 도울 수 있다. 다만 제안이 정확한지와 실제 환경에서 문제가 해결됐는지는 별도로 확인해야 한다.

내 생각에는 AI를 사용한다는 사실보다 어떤 권한을 주고 어떤 검토를 거치게 하는지가 더 중요하다. 패키지 선택부터 운영 환경 배포까지 자동화하면서 확인 절차를 생략하면 실수도 빠르게 퍼질 수 있다. 반대로 반복적인 확인을 돕는 용도로 사용하고 중요한 변경을 검증한다면 방어에 도움이 될 수 있을 것이다.

취약점을 찾아내는 것만으로 대응이 끝나지는 않는다. 수정안을 검토하고, 호환성을 확인하고, 배포하는 일도 필요하다. 오픈소스 관리자의 시간과 검토 여력이 부족하면 발견 이후의 대응이 늦어질 수 있다는 점도 함께 생각해야 한다.

## 배운 점과 느낀 점

공부하기 전에는 보안이 내가 작성한 코드를 안전하게 만드는 일이라고 생각했다. 하지만 무엇을 믿고 쓰는지 결정하는 것도 보안의 일부였다. 패키지를 설치하는 명령어 한 줄 뒤에는 그 패키지의 관리자와 의존성, 빌드·배포 과정이 연결돼 있었다.

나도 CTF나 과제를 할 때 검색해서 나온 패키지를 확인 없이 설치하곤 했다. 앞으로는 설치하기 전에 공식 프로젝트인지, 어떤 의존성이 함께 들어오는지 한 번 더 확인해 봐야겠다. AI가 추천하는 패키지도 마찬가지이다.

이번에는 개념과 사례를 중심으로 정리했다. 다음에는 내 프로젝트의 의존성을 직접 확인해 보고, SBOM으로 어떤 정보를 볼 수 있는지도 살펴볼 생각이다. 이번 OWASP Top 10에 새로 추가된 A10 부적절한 예외 처리도 이어서 공부해 보겠다.
